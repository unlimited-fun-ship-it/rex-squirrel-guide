State Machines — Squirrel Scripting in REX

State machines are a very useful tool in scripting — partly because of the lack of availability of some common algorithms in the older script syntax, and partly because of the turn‑based nature of the game. A great many things in a Total War campaign happen on a schedule or in a fixed sequence, and a state machine is the cleanest way to express both.

What is a state machine?

In programming, a state machine is a function that receives a state variable as its input and reacts accordingly. For each possible value of the state, there is an action associated with it (or not), and the state variable is often changed to move to the next state.

The state is just a number (or a string, or an enum) that represents “where in the sequence we currently are”. The function looks at the current state, decides what to do, and decides what the next state should be. On the next call, the process repeats.

Because a campaign runs turn by turn, a state machine fits naturally: one call per turn, one state transition per turn.

A simple state machine in Python

Here is a very simple state machine, written in Python for clarity. It has four states, numbered 0 to 3:

def state_machine(state):
    if state == 0:
        function1()
        state = 1
    elif state == 1:
        function2()
        state = 2
    elif state == 2:
        state = 0
    elif state == 3:
        function3()
        state = 2
    return state

Reading it:

  • If the state is 0, run function1 and move to state 1.
  • If the state is 1, run function2 and move to state 2.
  • If the state is 2, do nothing and move back to state 0.
  • If the state is 3, run function3 and move to state 2.

That is the whole idea. Everything below is just this pattern in the game’s own scripting languages.

The old RR example — a 3‑turn year

The most familiar use of a state machine in Rome: Total War scripting is the multi‑turn year. In vanilla, a year is two turns (summer, winter). Mods often want three, four, or more turns per year, with the season cycling accordingly.

Here is the classic RR approach, using a persistent counter as the state:

script
    declare_persistent_counter turn_number

    monitor_event NewTurnStart TrueCondition
        if I_CompareCounter turn_number = 0
            console_command season summer
        end_if
        if I_CompareCounter turn_number = 1
            console_command season summer
        end_if
        if I_CompareCounter turn_number = 2
            console_command season winter
            set_counter turn_number -1
        end_if
        inc_counter turn_number 1
    end_monitor
end_script

How it works:

  • turn_number is the state. It can be 0, 1, or 2.
  • On state 0 or 1, the season is set to summer.
  • On state 2, the season is set to winter, and the counter is set to -1.
  • At the end, the counter is incremented by 1. If it was -1, it becomes 0 — the cycle restarts.

Why -1 rather than 0? Because the increment happens at the end. Setting to -1 means that after the increment, the state is 0, ready for the next cycle. It is a small optimisation: the “reset” is folded into the increment that is going to happen anyway.

This works, but it is a little obscure. The next version of the same script is clearer:

script
    declare_persistent_counter turn_number

    monitor_event NewTurnStart TrueCondition
        declare_counter set_state
        set_counter set_state 0

        if I_CompareCounter turn_number = 0
            console_command season summer
            set_counter turn_number 1
            set_counter set_state 1
        end_if
        if I_CompareCounter turn_number = 1
              && I_CompareCounter set_state = 0
            console_command season summer
            set_counter turn_number 2
            set_counter set_state 1
        end_if
        if I_CompareCounter turn_number = 2
              && I_CompareCounter set_state = 0
            console_command season winter
            set_counter turn_number 0
            set_counter set_state 1
        end_if
    end_monitor
end_script

Now each state explicitly sets the next state, and the state change lives inside the if that handles it. The result is easier to read: “on state 0, do this and go to state 1; on state 1, do this and go to state 2; on state 2, do this and go to state 0”.

The Squirrel version

Squirrel is a real language, so the state machine collapses to something much closer to the Python original. There is no need for a persistent counter (event counters are already saved with the campaign), and there is no need for the set_state trick — Squirrel’s else if chain is inherently mutually exclusive.

Version A — compact, increment at the end

::events.on("NewTurnStart", function(payload) {
    local turnNumber = ::game.eventCounter("turn_number");
    if (turnNumber == null) turnNumber = 0;

    if (turnNumber == 0) {
        ::game.runScriptCommand("season", "summer");
    }
    else if (turnNumber == 1) {
        ::game.runScriptCommand("season", "summer");
    }
    else if (turnNumber == 2) {
        ::game.runScriptCommand("season", "winter");
        // Next turn we start the cycle again; the increment below
        // turns -1 into 0.
        turnNumber = -1;
    }

    ::game.setEventCounter("turn_number", turnNumber + 1);
});

Version B — explicit state transitions

::events.on("NewTurnStart", function(payload) {
    local turnNumber = ::game.eventCounter("turn_number");
    if (turnNumber == null) turnNumber = 0;

    if (turnNumber == 0) {
        ::game.runScriptCommand("season", "summer");
        ::game.setEventCounter("turn_number", 1);
    }
    else if (turnNumber == 1) {
        ::game.runScriptCommand("season", "summer");
        ::game.setEventCounter("turn_number", 2);
    }
    else if (turnNumber == 2) {
        ::game.runScriptCommand("season", "winter");
        ::game.setEventCounter("turn_number", 0);
    }
});

Version B is the direct translation of the second RR script and is the recommended style. Each branch handles its own state and writes its own next state, so the whole machine reads top to bottom.

Reading the season command

season is a campaign‑script command, not a Squirrel method, so it goes through ::game.runScriptCommand. If your build exposes a Campaign.season property (see the API docs), you can assign to that instead — the effect is the same:

::game.campaign.season = 2;   // 2 = summer in the four‑season numbering
Which to use? If Campaign.season is available, prefer it: it is a typed write and avoids the stringly‑typed command bridge. If not, ::game.runScriptCommand("season", …) is the reliable fallback and works in every build.

The set_state trick, and why Squirrel does not need it

In the second RR script, a set_state counter is used to make the following if statements behave like else if statements. Without it, if turn_number started at 0, the first if would fire, set turn_number to 1, and then the second if would also fire because turn_number is now 1 — and so on down the chain. The set_state counter is set to 1 by whichever branch fires, and every subsequent branch checks that it is still 0.

Squirrel has real else if, so this problem does not exist. A chain of if / else if / else if evaluates each condition in order and stops at the first one that matches, no matter what the earlier branch did to the state variable. The whole set_state mechanism disappears.

This is one of the biggest readability wins of moving to Squirrel. If you find yourself writing an I_CompareCounter … set_state = 0 guard in a new script, you are translating RR syntax by rote. Stop, and use else if instead.

A more intricate state machine

State machines are not limited to loops. You can branch, skip states, hold state until some condition is met, and so on. The following example runs a scripted storyline over several turns. It only advances from one state to the next when the player has done something specific, so the sequence can pause indefinitely.

The states:

0 → 1 → 2 → 3 → 4 → 5 ↺ 0

States 0, 2, and 4 fire a message and advance automatically. States 1, 3, and 5 wait for the player to capture a settlement before advancing.

::events.on("NewTurnStart", function(payload) {
    local state = ::game.eventCounter("story_state");
    if (state == null) state = 0;

    if (state == 0) {
        ::game.showHistoricEvent("senate_01",
            "The Story Begins",
            "A stranger arrives at your court with a proposal.");
        ::game.setEventCounter("story_state", 1);
    }
    else if (state == 1) {
        // Wait for the player to capture a settlement.
        if (::game.eventCounter("player_captured_settlement") == 1) {
            ::game.setEventCounter("player_captured_settlement", 0);
            ::game.setEventCounter("story_state", 2);
        }
    }
    else if (state == 2) {
        ::game.showHistoricEvent("senate_01",
            "A Debt Owed",
            "Your new ally demands payment.");
        ::game.setEventCounter("story_state", 3);
    }
    else if (state == 3) {
        if (::game.eventCounter("tribute_paid") == 1) {
            ::game.setEventCounter("tribute_paid", 0);
            ::game.setEventCounter("story_state", 4);
        }
    }
    else if (state == 4) {
        ::game.showHistoricEvent("senate_01",
            "Betrayal",
            "Your ally turns on you.");
        ::game.setEventCounter("story_state", 5);
    }
    else if (state == 5) {
        if (::game.eventCounter("ally_defeated") == 1) {
            ::game.setEventCounter("ally_defeated", 0);
            ::game.setEventCounter("story_state", 0);   // loop or stop
        }
    }
});

// The flags the state machine above waits on are set by other handlers.
::events.on("GeneralCaptureSettlement", function(payload) {
    if (::game.localFactionId() != payload.faction.id) return;
    ::game.setEventCounter("player_captured_settlement", 1);
});

::events.on("FactionDestroyed", function(payload) {
    if (payload.faction.name == "some_ally_faction") {
        ::game.setEventCounter("ally_defeated", 1);
    }
});

The pattern to notice: the state machine only reads and writes the state counter. Everything else — the events, the flags, the actual story — lives in separate handlers. This keeps each piece small and testable, and it means the state machine itself does not have to know anything about how the conditions are set.

Bridging a state machine to other scripts

The state variable is an event counter, which means it is visible to every other script, including the old RR major event scripts and spawn scripts. That is a feature, not a coincidence. If you want a major event to fire when the storyline reaches a particular point, read the state counter in the major event script:

;; In a major event script.
script
    if I_CompareCounter story_state = 4
        return true
    end_if
    return false
end_script

And if you want a Squirrel script to react to the storyline reaching a state, register a handler on the EventCounter event and check for the state change:

::events.on("EventCounter", function(payload) {
    if (payload.name != "story_state") return;
    if (payload.value == 4) {
        ::game.log("Story reached state 4 — triggering the climax.");
        // Do something extra here.
    }
});

This turns the state counter into a lightweight messaging bus: any part of the mod, whether Squirrel or engine‑scripted, can watch it and react.

Notes and pitfalls

  • Prefer else if over the set_state trick. Squirrel’s else if is mutually exclusive by definition. Do not port the set_state counter from RR scripts unless you have a specific reason to want two branches to be able to fire in the same pass.
  • Counters are null until first set. ::game.eventCounter returns null for a counter that has never been written. Always coalesce to a default before comparing, as the examples above do.
  • Event counters are saved with the campaign. This is what makes them the right home for a state variable. Do not use a persistent entry for the state — it will not survive a save/load.
  • Guard against re‑entry. If two events can bump the same state in the same turn, decide which one wins. The state machine should read the state at the top of its handler and write the next state exactly once.
  • Keep the state numeric. Strings work too, but a numeric state is easier to inspect in the log, easier to compare in a major event script, and easier to reason about.
  • Name the states. For anything more than three states, define named constants at the top of your script: 
    local STATE_INTRO       = 0;
local STATE_AWAIT_GIFT  = 1;
local STATE_GIFT_GIVEN  = 2;
local STATE_WAR         = 3;
local STATE_RESOLUTION  = 4;
    It costs nothing and turns a wall of magic numbers into readable logic.
  • Do not put heavy work in the state machine. The machine itself should be a thin dispatcher. The work belongs in separate functions that the machine calls.
  • Sketch the diagram before you write it. A state machine with more than four or five states is much easier to get right if you draw the states and arrows on paper first.
