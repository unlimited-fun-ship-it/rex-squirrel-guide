Major Event Scripts — Squirrel Scripting in REX

Major events — the engine calls them reforms, though they are used for much more than the Marian Reforms — are scripted conditions that permanently alter the campaign once they fire. They are checked every turn, and the moment the condition returns true, the event activates and its deactivate script (if any) takes over.

This page explains how major event scripts work in REX, and — the interesting part — how a Squirrel script can feed them, so that the trigger condition depends on anything Squirrel can observe.

What is a major event script?

A major event has up to two scripts attached:

  • An activation script — checked every turn. If it returns true, the event fires.
  • A deactivation script — optional; checked every turn once the event has fired. If it returns true, the event is undone.

Both live in data/major_event_scripts/ and are referenced from descr_sm_major_events.txt. They are written in the old RR script syntax (script … end_script), not in Squirrel — the engine reads them directly, one turn at a time. Squirrel cannot replace them; it can only influence them.

How they work

Every turn, the engine runs the activation script. The script must return true or return false:

  • return true — fire the major event.
  • return false — do nothing this turn; the event stays inactive.

Here is the vanilla Marian Reforms activation script, as an example:

script
    ;; Check every settlement in the world.
    for_each settlement in world
        if HasResource italy                                 ;; has the italy hidden resource
            && I_SettlementLevel local >= huge_city          ;; is a huge city
            && I_SettlementOwnerCulture local == roman       ;; the owner is Roman
            && not SettlementName Rome                       ;; the settlement isn't Rome

            return true   ;; trigger Marian Reforms
        end_if
    end_for

    return false   ;; don't trigger Marian Reforms
end_script

Notice the shape of this:

  • Inside the loop, return true exits the whole script immediately — so the first qualifying settlement wins.
  • If the loop finishes without returning, the script falls through to return false at the bottom.
  • There is no state kept between turns: the script simply re‑evaluates from scratch every time it runs.
Why does return false at the end work? When return is executed, the script stops there. So the outer return false is only reached if no earlier return true fired inside the loop. It is effectively the “nothing matched” fallback.

Bridging from Squirrel

Here is the catch: major event scripts cannot read Squirrel state directly. They cannot call into Squirrel, and Squirrel cannot hand them a persistent table entry or a live object reference. The two worlds only meet through the engine’s own shared data, and there are two shared things you can use:

  1. Event counters — the classic counters. Squirrel writes them with ::game.setEventCounter; the major event script reads them with I_CompareCounter.
  2. Hidden resources — per‑region flags. Squirrel writes them with Region.setHiddenResource; the major event script reads them with HasResource.

Both are checked by the engine every turn, so both are visible to a major event script. Which to use depends on what you are tracking:

ApproachGood forWatch out for
Event counter A single numeric value — “more than 5 spy missions”, “more than 100000 denarii spent”. The counter must exist before the major event script looks at it. Set it once at campaign load.
Hidden resource A boolean flag — “this specific thing has happened”, “the trigger is armed”. Hidden resources set at runtime are not saved; they are rebuilt from descr_regions on load, so Squirrel must re‑apply them on campaignMapLoaded.
What about persistent? A persistent table survives a script reload, but it is not the engine’s counter table and major event scripts cannot see it. Do not try to bridge through persistent. Use event counters (saved with the campaign) or hidden resources.

Worked example — spy missions trigger a reform

We want a reform to fire when the Julii have completed more than 5 spy missions. The Squirrel side counts the missions; the major event script reads the count and returns true once it crosses the threshold.

The Squirrel side (in your mod’s script folder)

// Make sure the counter exists before the major event script looks at it.
::events.on("campaignMapLoaded", function() {
    if (::game.eventCounter("spy_missions") == null) {
        ::game.setEventCounter("spy_missions", 0);
    }
});

// Count the Julii spy missions.
::events.on("SpyMission", function(payload) {
    local faction = payload.faction;
    if (faction == null) return;
    if (faction.name != "romans_julii") return;

    local count = ::game.eventCounter("spy_missions");
    if (count == null) count = 0;
    ::game.setEventCounter("spy_missions", count + 1);

    ::game.log("Julii spy missions: " + (count + 1));
});

The major event script (in data/major_event_scripts/)

script
    if I_CompareCounter spy_missions > 5
        return true
    end_if
    return false
end_script

That is all. Once the Squirrel handler has bumped spy_missions past 5, the major event script will return true on its next turn, and the reform fires.

Why this works. ::game.setEventCounter goes through the engine’s own command system, writing to the same counter table that I_CompareCounter reads.

The hidden‑resource variant

If for any reason the counter approach does not work in your build, the hidden‑resource trick is the fallback. Set an unclaimed resource flag on a settlement, and have the major event script check it.

Squirrel side:

::events.on("SpyMission", function(payload) {
    local faction = payload.faction;
    if (faction == null || faction.name != "romans_julii") return;

    local count = ::game.eventCounter("spy_missions");
    if (count == null) count = 0;
    count += 1;
    ::game.setEventCounter("spy_missions", count);

    if (count > 5) {
        // Set our flag on some known settlement. Any settlement will do;
        // the major event script only cares that the resource is set.
        local anchor = ::stratMap.findSettlement("Rome");
        if (anchor != null) {
            anchor.region.setHiddenResource("spy_reform_ready", true);
        }
    }
});

// Hidden resources are not saved — re‑apply on load.
::events.on("campaignMapLoaded", function() {
    local count = ::game.eventCounter("spy_missions");
    if (count != null && count > 5) {
        local anchor = ::stratMap.findSettlement("Rome");
        if (anchor != null) {
            anchor.region.setHiddenResource("spy_reform_ready", true);
        }
    }
});

Major event script side:

script
    for_each settlement in world
        if HasResource spy_reform_ready
            return true
        end_if
    end_for
    return false
end_script

The spy_reform_ready resource has to be declared in descr_regions.txt (or the equivalent resource list) so the engine will recognise the name. It does not have to be assigned to any region by default — it starts unset everywhere and Squirrel turns it on.

Notes and pitfalls

  • Major event scripts run every turn. They re‑evaluate from scratch. There is no “fire once” state on the script itself — the engine remembers whether the event has fired, and stops calling the activation script once it has.
  • They cannot read Squirrel state directly. Everything must flow through shared engine data: event counters, hidden resources, or the existing game state (ownership, buildings, etc.).
  • Counters must exist before the script looks at them. If the major event script tests I_CompareCounter spy_missions before Squirrel has ever called ::game.setEventCounter("spy_missions", …), the result is undefined. Initialise the counter in a campaignMapLoaded handler.
  • Hidden resources are not saved. Region.setHiddenResource edits the live region, but the change is rebuilt from descr_regions on load. Re‑apply the flag on campaignMapLoaded.
  • Return true stops the script. In the major event script, the first return true exits immediately. Anything after it — including the fallback return false — never runs.
  • Keep the trigger cheap. The script runs every turn for the whole campaign. Prefer an event counter comparison at the top over a full world scan, unless the scan is genuinely what you need.
  • The deactivate script is symmetric. It uses the same return true / return false shape, and it also runs every turn once the event is active. Bridge to it the same way.
  • Do not edit the vanilla major event scripts. Override them with your mod’s own versions in descr_sm_major_events.txt, so you do not break other mods and so your changes are tracked.
