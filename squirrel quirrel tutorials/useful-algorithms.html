Useful Algorithms — Squirrel Scripting in REX

This page collects small, self‑contained algorithmic patterns that come up again and again when scripting. Each entry explains what the algorithm does, why you might need it, and gives a Squirrel implementation you can copy straight into your mod.

Each algorithm is written assuming the REX Squirrel API, so it uses plain Squirrel arithmetic and the ::game.eventCounter / ::game.setEventCounter functions for persisted values. Where the original RR algorithm used counter_operation or holding_while, the Squirrel version replaces them with ordinary arithmetic and a while / for loop — Squirrel is a real language, so most of the old contortions simply disappear.

The % (modulo) operator — doing something every X turns

arithmetic periodic events every‑N‑turns

The % operator (called modulo, or mod) returns the remainder of a Euclidean division. So a = b % c sets a to the remainder left over when b is divided by c. For example, 7 % 3 is 1, and 9 % 3 is 0.

The classic use is “do something every X turns”: test turn % X == 0, and run the code when the test passes. That pattern fires on turn X, 2X, 3X, and so on.

The old RR approach

In RR, counters could not use the % operator directly, so the remainder had to be computed with a loop and a temporary counter:

;; RR — a = b % c
declare_counter temp
counter_operation temp = b - c
holding_while I_CompareCounter temp > 0
  counter_operation b = b - c
  counter_operation temp = b - c
end_while
declare_counter zero
set_counter zero 0
counter_operation a = b + zero

This works by repeatedly subtracting c from b until the result is zero or negative; the last non‑negative value of b is the remainder. It is correct, but it is slow, verbose, and hard to read.

The Squirrel version

Squirrel has the % operator built in, so the algorithm collapses to a single expression:

// a = b % c
local a = b % c;

There is no need for a temporary counter, a while loop, or a “zero” counter. The expression is evaluated directly.

Practical example — a periodic event every 5 turns

::events.on("NewTurnStart", function(payload) {
    local turn = ::game.eventCounter("turn_number");
    if (turn == null) turn = 0;

    // Every 5th turn (5, 10, 15, …).
    if (turn % 5 == 0 && turn > 0) {
        local player = ::campaign.factionById(::game.localFactionId());
        if (player != null) {
            player.money += 1000;
        }
    }
});

Practical example — a periodic event on a per‑object counter

::events.on("SettlementTurnStart", function(payload) {
    local s = payload.settlement;
    if (s == null) return;

    if (s.turnsOwned % 10 == 0 && s.turnsOwned > 0) {
        s.population += 200;
        ::game.log(s.name + " celebrates its " + s.turnsOwned + "-turn anniversary.");
    }
});

Notes and pitfalls

  • Squirrel’s % follows C semantics — the result takes the sign of the dividend. So -7 % 3 is -1, not 2. If you need a strictly non‑negative remainder, use ((b % c) + c) % c.
  • Guard against turn == 0 if you do not want the event to fire on turn 0. The modulo test alone will match it.
  • Integer only. Squirrel’s % works on integers. If you are working with floats, use fmod semantics yourself.
  • Do not repeat the RR loop. The holding_while construction from RR is not needed in Squirrel. Writing it out by hand would be a performance regression.

Running something an amount of times set in a counter

loops dynamic iteration

You want to repeat a block of code N times, where N is not a fixed number but the value of a counter (a number of units to spawn, a number of turns to simulate, a number of reinforcements to grant).

The old RR approach

RR’s for_each loop only iterates game lists, so a plain “do this N times” had to be built out of a holding_while loop and a temporary counter:

;; RR
declare_counter temp
declare_counter zero
set_counter zero 0
declare_counter a
set_counter a your_number
counter_operation temp = a + zero
holding_while I_CompareCounter temp > 0
  inc_counter temp -1
  ;; do something
end_while

The temporary counter temp starts at a, is decremented once per iteration, and stops when it reaches 0 — so the body runs exactly a times.

The Squirrel version

Squirrel has real for and while loops, so the algorithm is simply:

local a = ::game.eventCounter("a_counter");
if (a == null) a = 0;

for (local i = 0; i < a; i++) {
    // do something — this runs `a` times
}

If you also need the iteration number (say, to name a spawned unit or to apply a different effect on the first pass), use the loop variable directly:

for (local i = 0; i < a; i++) {
    ::game.log("Iteration " + i + " of " + a);
}

If you prefer a while loop — for example, because you also want to mutate a inside the body — that works too:

local remaining = a;
while (remaining > 0) {
    // do something
    remaining -= 1;
}

Practical example — spawn N units, where N is a counter

::events.on("FactionTurnStart", function(payload) {
    local faction = payload.faction;
    if (faction == null) return;

    local count = ::game.eventCounter("reinforcement_count");
    if (count == null) count = 0;

    local capital = faction.capital;
    if (capital == null) return;

    local army = capital.army;
    if (army == null) return;

    for (local i = 0; i < count; i++) {
        army.createUnit("roman hastati", 0, 0, 0, -1);
    }

    ::game.log("Spawned " + count + " hastati in " + capital.name + ".");
});

Notes and pitfalls

  • Counter may be null. ::game.eventCounter returns null when the counter does not yet exist. Always coalesce it (as above) before using it in a loop condition.
  • Do not mutate the loop variable. In a for loop, changing i inside the body has no defined effect on the iteration. If you need that behaviour, use while.
  • Use the right range. for (local i = 0; i < a; i++) runs exactly a times — not a + 1, and not a - 1. Watch for off‑by‑one errors when porting old code that used different comparison operators.
  • Break early if you need to. Squirrel supports break and continue, which are often cleaner than RR’s terminate_monitor tricks.

Multiple outcomes random operation (weighted selection)

random weighted choice branching

Pick one of several possible outcomes at random, with each outcome carrying a specified probability. In most languages this is a simple if / else if chain over a random number.

The old RR approach

In RR, RandomPercent could not be assigned to a counter — it could only appear inside a condition. So a chain of independent tests had to be used, with a “taken” flag to make sure only the first matching test ran:

;; RR — four equally likely outcomes
declare_counter chance_taken
set_counter chance_taken 0

if RandomPercent <= 25
  set_counter chance_taken 1
  ;; result 1
end_if

if RandomPercent <= 33
   && I_CompareCounter chance_taken = 0
  set_counter chance_taken 1
  ;; result 2
end_if

if RandomPercent <= 50
   && I_CompareCounter chance_taken = 0
  set_counter chance_taken 1
  ;; result 3
end_if

if I_CompareCounter chance_taken = 0
  ;; result 4
end_if

Even though it looks like it, this gives each outcome a 25% chance. The reason is that the tests are evaluated in sequence against the remaining probability space:

  • Outcome 1 wins 25% of the time. When it does, chance_taken is set and the rest are skipped.
  • If outcome 1 loses (75% of the time), three outcomes are left, so outcome 2 should win 1/3 of those cases. 1/3 × 75% = 25%.
  • The same logic gives outcome 3 a 1/2 × (remaining 50%) = 25% chance, and outcome 4 the final 25%.

In general, for a set of outcomes o₁, o₂, …, oₙ, …, o_f (with o_f the final fallback) with desired probabilities p₁, p₂, …, pₙ, …, p_f, the threshold you write into the script for outcome oₙ is:

rₙ = pₙ / (pₙ + pₙ₊₁ + … + p_f)

For four equal outcomes: r₁ = 1/4 = 25%, r₂ = 1/3 ≈ 33%, r₃ = 1/2 = 50%, and the fallback is unconditional.

The Squirrel version

Squirrel has rand(), which returns an integer. Taking rand() % 100 gives a value from 0 to 99, and a straight if / else if chain does the rest:

// Four equally likely outcomes.
local roll = rand() % 100;   // 0..99

if (roll < 25) {
    // result 1  (25%)
} else if (roll < 50) {
    // result 2  (25%)
} else if (roll < 75) {
    // result 3  (25%)
} else {
    // result 4  (25%)
}

Because the thresholds are cumulative, the else if chain already guarantees “the first matching test wins” — no chance_taken counter is needed, and no per‑outcome re‑derivation. Each threshold tₙ is just the running total of all previous probabilities:

tₙ = p₁ + p₂ + … + pₙ

Practical example — unequal weights

Suppose you want a 50% chance of result 1, a 30% chance of result 2, and a 20% chance of result 3:

local roll = rand() % 100;

if (roll < 50) {
    // result 1  (50%)
} else if (roll < 80) {          // 50 + 30
    // result 2  (30%)
} else {
    // result 3  (20%)
}

Practical example — scripting a random event on a turn

::events.on("FactionTurnStart", function(payload) {
    local faction = payload.faction;
    if (faction == null) return;
    if (::game.localFactionId() != faction.id) return;

    local roll = rand() % 100;

    if (roll < 10) {
        // 10% — rare bad event
        ::game.showHistoricEvent("senate_01", "Bad News",
            "Bandits are raiding your countryside.");
    } else if (roll < 30) {
        // 20% — minor good event
        faction.money += 200;
    } else if (roll < 60) {
        // 30% — nothing happens
    } else {
        // 40% — silent
    }
});

Notes and pitfalls

  • Always leave a fallback. Finish with a plain else so that any unexpected value is handled. If your thresholds sum to less than 100, the else branch absorbs the remainder.
  • Do not compare rand() % 100 with <= by accident. < gives the threshold as a percentage directly. <= 25 would include 25 in the first bucket, making that bucket 26%.
  • Roll once per event. If you need several independent random decisions, call rand() % 100 once per decision. Do not roll once and reuse the value for multiple questions.
  • Do not reproduce the RR derivation. The RR version needed the probability formula rₙ = pₙ / (sum of remaining p) because each test was independent. Squirrel’s else if chain makes each test conditional on the previous ones failing, so the plain cumulative thresholds are correct.

Checking if a settlement changed hands

state tracking settlement ownership

You want to detect when a settlement is captured, traded, or otherwise transferred from one faction to another — for example, to run a “the city has fallen” message, to destroy specific buildings, or to update your own per‑settlement bookkeeping.

The old RR approach

RR had no native “owner changed” event, so the standard technique was to assign each faction a numeric id, store that id on every settlement, and then poll at the start of each turn:

;; RR — assign each faction a numeric id
declare_counter faction_id
for_each faction in world
  store_counter faction_id faction l_faction_id
  inc_counter faction_id 1
end_for

;; At game start, tag every settlement with its owner's id
for_each faction in world
  declare_counter faction_id
  retrieve_counter l_faction_id faction faction_id

  for_each settlement in faction
    store_counter faction_id settlement l_owner_id
  end_for
end_for

;; On each new turn, compare the current owner with the stored one
monitor_event NewTurnStart TrueCondition
  for_each faction in world
    declare_counter faction_id
    retrieve_counter l_faction_id faction faction_id

    for_each settlement in faction
      declare_counter previous_owner_id
      retrieve_counter l_owner_id settlement previous_owner_id
      if I_CompareCounter faction_id != previous_owner_id
        store_counter faction_id settlement l_owner_id
        ;; do something — the settlement has changed hands
      end_if
    end_for
  end_for
end_monitor

This works, but it needs two for_each loops per turn, it relies on a hand‑rolled id scheme, and it only catches changes at turn boundaries — a settlement captured and lost in the same turn would never be noticed.

The Squirrel version

REX exposes the change directly. The cleanest approach is to listen for the event that fires when a settlement is captured:

::events.on("GeneralCaptureSettlement", function(payload) {
    local settlement = payload.settlement;
    local newOwner   = payload.faction;
    if (settlement == null || newOwner == null) return;

    ::game.log(settlement.name + " has fallen to " + newOwner.name + ".");

    // Do your per-capture work here.
    newOwner.money += 500;
});
Check the payload. The exact field names on the payload are documented in api.d.nut. If you are unsure, log the payload first: 
::events.on("GeneralCaptureSettlement", function(payload) {
    ::game.log("Payload: " + payload);
});

If you need to catch every kind of transfer, not just conquest

Settlements can also change hands by trade, by script, or by being given away. To catch those, or to keep a history of owners, track the current owner id in a persistent table keyed by the settlement’s index, and compare it on a turn boundary:

// At pluginLoad, make sure our table exists.
::events.on("pluginLoad", function() {
    if (!("lastOwner" in persistent))
        persistent.lastOwner <- {};
});

::events.on("NewTurnStart", function(payload) {
    for (local i = 0; i < ::stratMap.regionCount(); i++) {
        local region = ::stratMap.region(i);
        if (region == null) continue;

        local s = region.settlement;
        if (s == null) continue;

        local newOwnerId = (s.owner == null) ? -1 : s.owner.id;
        local key = s.index;

        if (!(key in persistent.lastOwner)) {
            persistent.lastOwner[key] <- newOwnerId;
            continue;
        }

        local oldOwnerId = persistent.lastOwner[key];
        if (newOwnerId != oldOwnerId) {
            persistent.lastOwner[key] <- newOwnerId;

            local oldOwner = ::campaign.factionById(oldOwnerId);
            local newOwner = ::campaign.factionById(newOwnerId);
            ::game.log(s.name + " transferred from "
                + (oldOwner == null ? "nobody" : oldOwner.name)
                + " to "
                + (newOwner == null ? "nobody" : newOwner.name) + ".");
        }
    }
});

Native properties worth knowing

You may not even need to track anything yourself. The Settlement class already exposes:

  • Settlement.owner — the current owning faction (read/write).
  • Settlement.previousOwnerId — the id of the faction that owned it before the current one.
  • Settlement.tradedFromId — the faction it was traded from, or -1 if taken by force.
  • Settlement.turnsOwned — how many turns the current owner has held it.

With those, distinguishing a conquest from a trade is a one‑line test:

::events.on("GeneralCaptureSettlement", function(payload) {
    local s = payload.settlement;
    if (s == null) return;

    if (s.tradedFromId == -1) {
        ::game.log(s.name + " was captured by force.");
    } else {
        ::game.log(s.name + " was traded.");
    }
});

Notes and pitfalls

  • Choose the right trigger. GeneralCaptureSettlement fires on conquest. If you need to catch trades and script‑driven transfers too, use the polling pattern with persistent (or the native tradedFromId field).
  • Polling only sees turn boundaries. A settlement captured and lost within a single turn will be missed by a NewTurnStart scan. Use the event if you need to catch every transition.
  • Persistent is not saved. A persistent table survives a script reload (::game.reloadScripts()) but is not written to the campaign save. If you need the last‑owner tracking to survive a save/load, store the value in an event counter named after the settlement, or rebuild the table on campaignMapLoaded.
  • Use a stable key. Settlement.index is stable for the life of the campaign, so it is safe as a table key. Do not key by display name — players can rename settlements.

First‑time setup

initialisation one‑shot

You want a block of code to run exactly once per campaign — setting up initial diplomatic stances, giving a specific faction starting money, applying a scripted bonus based on which faction the player chose, and so on. The challenge is that a naive “turn 0” check will fire again every time the player saves and reloads on that turn.

The old RR approach

RR solved this with a persistent counter that acted as a “have we run yet?” flag:

;; RR
declare_persistent_counter first_time_setup

if I_CompareCounter first_time_setup = 0
    ;; do your once‑only stuff here
    if not I_LocalFaction romans_etruscans
        console_command become_protector romans_julii romans_etruscans
    end_if

    console_command diplomatic_stance romans_etruscans romans_brutii war

    ;; set the flag — on the next load this will be 1 and the block will be skipped
    set_counter first_time_setup 1
end_if

The persistent counter is serialised with the save, so the block runs exactly once.

The Squirrel version

Squirrel has two equally good approaches. Choose based on whether you want the block to run for new campaigns only, or for any campaign the script finds itself in — including a campaign started before the script was installed.

Approach A — new campaigns only, via newGameLoaded

The newGameLoaded event fires when a brand‑new campaign’s world data has been built. Loading a save does not go through this hook, so anything registered on it runs exactly once per fresh campaign:

::events.on("newGameLoaded", function() {
    // This runs once, when a new campaign starts. It will not run on load.
    local etruscans = ::campaign.factionByName("romans_etruscans");
    local julii      = ::campaign.factionByName("romans_julii");
    local brutii     = ::campaign.factionByName("romans_brutii");

    if (etruscans != null && julii != null
        && ::game.localFactionId() != etruscans.id) {
        ::game.runConsoleCommand("become_protector",
            "romans_julii romans_etruscans");
    }

    if (etruscans != null && brutii != null) {
        ::campaign.setStance(::Enum.DiplomaticRelation.war, etruscans, brutii);
    }
});

This is the most direct replacement for the RR pattern, and it is the right choice when your script is installed before the campaign begins.

Approach B — any campaign, via a flag counter

If your script may be added to a campaign that is already underway, or you want the safety of an explicit flag regardless of how the script got there, use an event counter:

::events.on("campaignMapLoaded", function() {
    // campaignMapLoaded fires every time the strat map opens, so we need a
    // guard that persists across loads and inside the save.
    if (::game.eventCounter("first_time_setup") == 1) return;

    local etruscans = ::campaign.factionByName("romans_etruscans");
    local julii      = ::campaign.factionByName("romans_julii");
    local brutii     = ::campaign.factionByName("romans_brutii");

    if (etruscans != null && julii != null
        && ::game.localFactionId() != etruscans.id) {
        ::game.runConsoleCommand("become_protector",
            "romans_julii romans_etruscans");
    }

    if (etruscans != null && brutii != null) {
        ::campaign.setStance(::Enum.DiplomaticRelation.war, etruscans, brutii);
    }

    ::game.setEventCounter("first_time_setup", 1);
});
Why an event counter and not persistent? The persistent table survives a script reload but is not written into the campaign save. Event counters are saved with the campaign, which is exactly what a first‑time‑setup flag needs. The RR pattern used a persistent counter because that was the only tool RR had; in REX the two ideas are distinct, and the event counter is the right one for this job.

Practical example — choose a starting bonus based on the player’s faction

::events.on("newGameLoaded", function() {
    local player = ::campaign.factionById(::game.localFactionId());
    if (player == null) return;

    if (player.name == "romans_julii") {
        player.money += 5000;
    } else if (player.name == "romans_brutii") {
        local capital = player.capital;
        if (capital != null && capital.army != null) {
            capital.army.createUnit("roman princeps", 2, 0, 0, -1);
        }
    } else if (player.name == "romans_scipii") {
        // grant a temporary movement boost, or any other one‑off effect
    }

    ::game.showHistoricEvent("senate_01",
        "Campaign Started",
        "Your faction has received its starting blessing.");
});

Notes and pitfalls

  • Pick the right event. newGameLoaded fires only for brand‑new campaigns. campaignMapLoaded fires every time the map opens (including returning from a battle) and needs a flag. GameReloaded fires when a save is loaded.
  • Do not rely on turn == 0. A turn‑based check re‑fires whenever the player loads a save made on that turn. Always use a counter or the appropriate event.
  • Event counters start as null, not 0. ::game.eventCounter("name") returns null for a counter that has never been set. Compare against null or coalesce to 0 before testing == 0.
  • Prefer named flags over magic strings. Use a descriptive counter name like "first_time_setup" rather than a generic one, so the intent is clear when reading the script later.
