Basic Tools — Squirrel Scripting in REX

The basic tools to write a Squirrel script are Events, Conditions, and Commands. In the old RR scripting these were three separate concepts with their own syntax and their own reference lists. In Squirrel they collapse into one idea: everything is code.

  • Events are registered with ::events.on(name, handler).
  • Conditions are ordinary if statements.
  • Commands are ordinary function or method calls on game objects.

There is no separate list of commands, conditions, and events in the way RR had. The single reference for everything you can do is api.d.nut — the generated API documentation that ships with REX. It lists every global table (::game, ::stratMap, ::ui, ::events, ::campaignDb, ::buildings, …), every class (Faction, Settlement, Army, Character, Unit, Region, …), and every event name. Treat it as the equivalent of RR’s four documentation files, all rolled into one.

For a quick look at the event names without opening the file, search api.d.nut for the ::events table — the trigger events are listed as one‑line comments (// FactionTurnStart, // BuildingCompleted, // CharacterTurnEnd, and so on).

Frequently Used Patterns

::events.on — the replacement for monitor_event

This is the workhorse. It registers a handler function that runs whenever the named event fires.

::events.on("NewTurnStart", function(payload) {
    // code that runs whenever a new turn begins
});
  • The first argument is the event name — the same names RR used (NewTurnStart, BuildingCompleted, CharacterTurnEnd, CityRebels, …).
  • The second argument is a function. REX calls it whenever the event fires.
  • The function receives a payload object whose fields depend on the event. Read the fields you need off it by name. If unsure, log the payload:
::events.on("NewTurnStart", function(payload) {
    ::game.log("Payload: " + payload);
});

Unlike monitor_event, there is no end_monitor. The handler is a normal function — it ends when the function ends.

Conditions

There is no and keyword and no condition list. Any check you would have written as monitor_event ... and I_CompareCounter ... and RandomPercent <= 5 becomes a plain if:

::events.on("NewTurnStart", function(payload) {
    local counter = ::game.eventCounter("a_counter");
    if (counter == null) counter = 0;

    ::game.setEventCounter("a_counter", counter + 1);
    if (counter + 1 > 5) {
        // terminate_monitor equivalent — see below
    }
});

You can call the same helper functions old scripts used, via ::game:

“Terminating” a handler

RR had terminate_monitor to stop a monitor from firing again. Squirrel has no such thing — a handler function is registered once and stays registered. To stop it from doing anything, guard it with a flag:

::events.on("NewTurnStart", function(payload) {
    if (::game.eventCounter("my_monitor_done") == 1) return;

    // ... do the work ...

    ::game.setEventCounter("my_monitor_done", 1);
});

Or, if you want the handler gone entirely (saves a small amount of per‑event overhead), you can keep a reference to the function and remove it — but the simple guard above is the recommended pattern and what most mods use.

monitor_conditions — the replacement

RR’s monitor_conditions polled a condition on every tick. The direct Squirrel equivalent is a handler on a tick event:

::events.on("campaignTick", function(payload) {
    if (::game.eventCounter("a_counter") <= 5) return;

    // ... condition met, do the work ...
});
Be careful with campaignTick and battleTick — they fire many times per second. Do not do heavy work in them.

Loops (for_each)

RR’s for_each … end_for loop iterated over a game list (settlements, units, factions, characters, armies, forts, regions). In Squirrel you use a normal for loop, and you read the list off the object that owns it.

RR example — count every Julii settlement that has the italy resource:

for_each settlement in faction "romans_julii"
  if HasResource italy
    inc_counter a_counter 1
  end_if
end_for

Squirrel equivalent:

local julii = ::campaign.factionByName("romans_julii");
if (julii != null) {
    for (local i = 0; i < julii.settlementCount; i++) {
        local s = julii.settlement(i);
        if (s == null) continue;
        if (s.region.hasHiddenResource("italy")) {
            local c = ::game.eventCounter("a_counter");
            ::game.setEventCounter("a_counter", c + 1);
        }
    }
}

Or, using the region’s own list:

for (local i = 0; i < ::stratMap.regionCount(); i++) {
    local r = ::stratMap.region(i);
    if (r == null) continue;
    if (r.faction == null || r.faction.name != "romans_julii") continue;
    if (r.hasHiddenResource("italy")) {
        local c = ::game.eventCounter("a_counter");
        ::game.setEventCounter("a_counter", c + 1);
    }
}

The local keyword

RR used local (or local_settlement, local_faction, etc.) to refer to the current iteration of a for_each loop. In Squirrel there is no local — you simply keep a reference to the object you are iterating. The variable you assigned is the “local” object:

for (local i = 0; i < faction.settlementCount; i++) {
    local settlement = faction.settlement(i);   // <-- this is your "local"
    if (settlement == null) continue;

    // do stuff with `settlement`
}

This is clearer and safer than RR’s local, which could silently refer to the wrong thing if the scope was ambiguous.

Storing counters on objects

RR’s store_counter / retrieve_counter let you attach a counter to a settlement, character, unit, or faction. In Squirrel you have two options:

1. Use a native property if one already exists. For example, Settlement.turnsOwned.

2. Keep your own table in persistent, keyed by the object’s index. This is the direct replacement for store_counter:

::events.on("pluginLoad", function() {
    if (!("settlementCounters" in persistent))
        persistent.settlementCounters <- {};
});

::events.on("SettlementTurnStart", function(payload) {
    local s = payload.settlement;
    local key = s.index;

    if (!(key in persistent.settlementCounters))
        persistent.settlementCounters[key] <- {};

    local store = persistent.settlementCounters[key];
    if (!("myCounter" in store)) store.myCounter <- 0;
    store.myCounter += 1;
});
Remember: persistent survives a script reload but not a save/load. For data that must persist in the save, use event counters (which the engine serialises) or a native property that is already saved.

console_command

RR’s console_command ran a RomeShell command from inside a script. In Squirrel most of those commands have a direct method on the relevant object. Where they do not, you can still call the console verb through ::game.runConsoleCommand.

Preferred: method calls

// RR:
// console_command add_money romans_julii 1000

local julii = ::campaign.factionByName("romans_julii");
if (julii != null) julii.money += 1000;
// RR:
// console_command create_unit "Rome" "roman hastati" 4 0 0 0

local rome = ::stratMap.findSettlement("Rome");
if (rome != null) {
    local army = rome.createGarrisonArmy();
    if (army != null) {
        army.createUnit("roman hastati", 4, 0, 0, -1);
    }
}
// RR:
// console_command kill_character "Julius"

local c = ::campaign.findCharacterByLabel("Julius");
if (c != null) c.kill();

Fallback: runConsoleCommand

If a verb has no method equivalent (or you are porting an old script and want a quick translation), use ::game.runConsoleCommand:

::game.runConsoleCommand("add_money", "romans_julii 1000");
Use this sparingly. Console commands bypass the object model and are harder to debug. If a proper method exists, prefer it.

Counters

Counters still exist in REX and are serialised with the campaign. There is one kind now — the persistent counter from RR — because REX does not have the old “regular counter that dies on reload” distinction. Every counter written through ::game.setEventCounter is saved.

Declaring, reading, writing

// Read (null if it doesn't exist yet).
local value = ::game.eventCounter("a_counter");

// Write (creates the counter if absent).
::game.setEventCounter("a_counter", 3);

// Increment.
::game.setEventCounter("a_counter", value + 5);

// Decrement.
::game.setEventCounter("a_counter", value - 1);

Operations

RR had counter_operation to do arithmetic between counters. In Squirrel this is just arithmetic:

local resultCounter = ::game.eventCounter("counter_1")
                   + ::game.eventCounter("counter_2");
::game.setEventCounter("result_counter", resultCounter);

Because you are operating on plain integers, you can mix in literals freely — there is no need to declare a “three” counter as RR required:

local c = ::game.eventCounter("a_counter");
::game.setEventCounter("result_counter", c + 3);

Comparison

RR’s I_CompareCounter becomes a plain comparison, and you can compare two counters directly:

if (::game.eventCounter("a_counter") == 3) {
    // ...
}

if (::game.eventCounter("counter_1") > ::game.eventCounter("counter_2")) {
    // ...
}

Combining conditions with parentheses

RR used and, or, and parentheses to combine conditions. Squirrel uses the standard C operators && (and) and || (or), with the same parentheses rules — and no ambiguity, because the precedence of && over || is fixed by the language.

RR examples, translated:

// All conditions must be met.
if (unit.type.name == "roman hastati"
    && ::game.eventCounter("turn_number") == 1
    && settlement.name == "Rome") {
    // ...
}
// Any condition will do.
if (unit.type.name == "roman hastati"
    || ::game.eventCounter("turn_number") == 1
    || settlement.name == "Rome") {
    // ...
}
// Mixed — parentheses remove ambiguity, just as in RR.
if (unit.type.name == "roman hastati"
    && (::game.eventCounter("turn_number") == 1
        || settlement.name == "Rome")) {
    // Hastati AND (turn 1 OR Rome)
}
if (settlement.name == "Rome"
    || (::game.eventCounter("turn_number") == 1
        && unit.type.name == "roman hastati")) {
    // Rome OR (turn 1 AND hastati)
}
Precedence: && binds tighter than ||, so a || b && c means a || (b && c). When in doubt, add parentheses. It costs nothing and reads better.

Yes/No events for the player

RR’s message_prompt command paired with the ScriptPromptCallback event let a script ask the player a yes/no question. In REX this becomes two pieces:

  1. Raise the prompt with ::campaign.raiseEvent(...), passing isChoice = true. REX shows Accept / Decline buttons and automatically bumps two event counters: <name>_accepted and <name>_declined.
  2. Handle the answer by listening for the EventCounter event and checking which counter changed.

The old RR pattern (for reference)

declare_counter new_legion_flag
declare_counter new_legion_result

message_prompt
{
  flag_counter new_legion_flag
  result_counter new_legion_result
  title new_legion_possible_title
  body new_legion_possible_body
  image marian_reform
}

monitor_event ScriptPromptCallback I_CompareCounter new_legion_flag = 1
    if I_CompareCounter new_legion_result = 1
        inc_counter local_number_of_legions_julii 1
        for_each settlement in faction "romans_julii"
            if IsCapital
                console_command create_unit local_settlement "roman hastati" 4 0 0 0
                console_command create_unit local_settlement "roman princeps" 4 0 0 0
                console_command create_unit local_settlement "roman triarii" 2 0 0 0
                console_command add_population local -500
                console_command add_money romans_julii, -4000
            end_if
        end_for
    end_if
end_monitor

The Squirrel version

// 1. Raise the prompt when the conditions are met.
::events.on("FactionTurnStart", function(payload) {
    local faction = payload.faction;
    if (faction == null) return;
    if (faction.name != "romans_julii") return;
    if (::game.localFactionId() != faction.id) return;

    // Only offer once — guard with a flag counter.
    if (::game.eventCounter("new_legion_offered") == 1) return;

    // Conditions: e.g. Mariana reforms active and the treasury is deep.
    if (!faction.record) return;
    if (faction.money < 4000) return;

    ::campaign.raiseEvent(
        "marian_reform",                      // picture name and counter base
        ::game.text("new_legion_possible_title"),
        ::game.text("new_legion_possible_body"),
        true,                                 // isChoice = true
        -1, -1,                               // no map position
        [faction.id]                          // only show to Julii
    );

    ::game.setEventCounter("new_legion_offered", 1);
});

// 2. Handle the player's answer.
::events.on("EventCounter", function(payload) {
    if (payload.name == "marian_reform_accepted" && payload.value == 1) {
        local julii = ::campaign.factionByName("romans_julii");
        if (julii == null) return;

        // Increment the running total of legions.
        local total = ::game.eventCounter("local_number_of_legions_julii");
        ::game.setEventCounter("local_number_of_legions_julii", total + 1);

        // Find the Julii capital and spawn the legion there.
        local capital = julii.capital;
        if (capital != null) {
            local garrison = capital.army;   // the garrison stack
            if (garrison != null) {
                garrison.createUnit("roman hastati",  4, 0, 0, -1);
                garrison.createUnit("roman princeps", 4, 0, 0, -1);
                garrison.createUnit("roman triarii",  2, 0, 0, -1);
            }
            capital.population -= 500;
        }

        julii.money -= 4000;

        // Reset the accepted counter so the callback only fires once.
        ::game.setEventCounter("marian_reform_accepted", 0);
    }
    else if (payload.name == "marian_reform_declined" && payload.value == 1) {
        // Player said no — do nothing, but reset the counter.
        ::game.setEventCounter("marian_reform_declined", 0);
    }
});

Reset the accepted / declined counters after handling them. They are normal event counters and will stay at 1 otherwise, which means the EventCounter event will not re‑fire when the same choice is raised a second time.
If ::campaign is not available in your REX build, check the REX documentation for the correct accessor (it may be ::game.campaign, or a global exposed under a different name). The object you want is the one with raiseEvent, factionById, factionByName, and settlementByName.

Important: where handlers may live

RR forbade putting a monitor_event inside another monitor, and forbade monitors inside reform or emergent‑faction triggers. In Squirrel those restrictions are gone. You can register a handler from inside another handler, from inside a function, from inside a loop — anywhere.

The one rule to keep in mind is that registering the same handler twice registers it twice. REX does not de‑duplicate. If a handler runs on a frequently‑firing event, guard the registration:

::events.on("pluginLoad", function() {
    // Register turn handlers exactly once.
    ::events.on("FactionTurnStart", onFactionTurnStart);
});

Because pluginLoad fires only when the script world loads, this is the safe place for one‑shot registrations.
