Introduction to Squirrel Scripting in REX

Scripting has been greatly expanded in the REX Community Patch. This short article will try to give you some of the highlights, focusing on what is new or different compared to the old Rome Remastered (RR) scripting system. The examples are written for the Squirrel API.

What is Squirrel?

Squirrel is a lightweight, C‑like scripting language embedded in REX. Unlike the old line‑based scripting, it is a real programming language with variables, functions, classes, and events. You write .nut files, place them in your mod’s script folder (note: singular — not scripts), and REX loads them at runtime.

The two main ideas to understand are:

  • Lifecycle hooks – code that runs at a fixed point in the game’s life, like pluginLoad, gameInit, newGameLoaded, campaignMapLoaded, unloadCampaign.
  • Event handlers – code that runs in response to something happening, like FactionTurnStart, CharacterTurnEnd, BuildingCompleted, CityRebels, or EventCounter.

Both are registered with ::events.on(name, handler).

Script loading

There is no script / end_script block, and no descr_strat entry. A .nut file placed in the mod’s script folder is loaded automatically. Multiple files can run side‑by‑side. The scripting runtime starts with a hook called pluginLoad, which fires once the entry script has finished loading — before any game exists.

::events.on("pluginLoad", function() {
    ::game.log("Script world loaded.");
    ::game.log("API version: " + ::scripting.apiVersion());
    ::game.log("Port: " + ::scripting.port());   // "romans" or "medieval2"
});

Counters and persistent state

The classic counters still exist — you can read and write them from Squirrel. They go through the engine’s own command system, so any old‑style monitor watching them will still fire.

// Read an event counter (null if it doesn't exist).
local value = ::game.eventCounter("my_counter");

// Write one (creating it if needed).
::game.setEventCounter("my_counter", 5);

For counters that need to survive script reloads (::game.reloadScripts()), REX provides a persistent table. Anything you store there is carried across into the new script world.

persistent.firstTimeSetup <- true;

Be careful: persistent is about the script runtime, not the campaign save. For state that must survive save/load, use event counters, or store data on the objects themselves (see below).

A first‑time setup, for example, looks like this:

::events.on("campaignMapLoaded", function() {
    if (::game.eventCounter("first_time_setup") == 1) return;

    local parthia = ::campaign.factionByName("parthia");
    if (parthia != null) parthia.money += 40000;

    ::game.setEventCounter("first_time_setup", 1);
});
Note: if ::campaign is not exposed in your build, see the section “Finding the Campaign object” at the end.

Event payloads — the new “local scope”

In RR, the local keyword let a monitor refer to whatever object the event was about. In REX this is replaced by event payloads. Every engine trigger event passes a single payload object to your handler, and you read the fields you need off it by name.

// A building called "abandon_settlement" was completed.
::events.on("BuildingCompleted", function(payload) {
    if (payload.building.chainName == "abandon_settlement") {
        payload.settlement.provokeRebellion();
    }
});

// A city rebelled — destroy the building if it exists.
::events.on("CityRebels", function(payload) {
    local building = payload.settlement.buildingOfChain("abandon_settlement");
    if (building != null) building.destroy();
});

The field names on the payload vary per event — check api.d.nut under the ::events table, and if you are unsure, log the payload:

::events.on("SomeEvent", function(payload) {
    ::game.log("Payload: " + payload);
});

Loops

Squirrel has real for, foreach, and while loops — no for_each ... end_for needed.

// Kill every character in a faction after turn 5.
::events.on("NewTurnStart", function() {
    if (::game.eventCounter("turn_number") <= 5) return;

    local host = ::campaign.factionByName("brennus_host");
    if (host == null) return;

    for (local i = 0; i < host.characterCount; i++) {
        local c = host.character(i);
        if (c != null) c.kill();
    }
});

Or iterate an array directly:

foreach (record in someCharacter.children()) {
    ::game.log("Child: " + record.displayName);
}

Storing extra data on objects

In RR you used store_counter / retrieve_counter to attach arbitrary values to settlements, characters, units, or factions. In REX you have two far cleaner options:

1. Use the object’s own properties. Most things you would want to track are already there.

::events.on("SettlementTurnStart", function(payload) {
    local s = payload.settlement;
    s.turnsOwned += 1;          // native property, saved with the campaign
    ::game.log(s.name + " owned for " + s.turnsOwned + " turns.");
});

2. Keep a Squirrel table in persistent, keyed by the object. This is the right way to track custom data that has no native property.

// At pluginLoad, make sure our data table exists.
::events.on("pluginLoad", function() {
    if (!("settlementData" in persistent))
        persistent.settlementData <- {};
});

::events.on("SettlementTurnStart", function(payload) {
    local s = payload.settlement;
    local key = s.index;        // a stable id for the settlement

    if (!(key in persistent.settlementData))
        persistent.settlementData[key] <- { ownedTurns = 0 };

    persistent.settlementData[key].ownedTurns += 1;
});

Remember that persistent is lost when the player saves and reloads the campaign — only the script runtime reload keeps it. For save‑compatible data, use event counters or the object’s own properties.

Logging

Logging is much better than in RR. Two things help immediately:

  • ::game.log(message) writes a line to the engine log under the script channel. Use it liberally.
  • ::game.showHistoricEvent(picture, title, body) raises a historic‑event popup to the player (a one‑way message, no choice).
::game.log("Turn " + ::game.eventCounter("turn_number") + ": treasury is low.");
::game.showHistoricEvent("senate_01", "Warning", "The treasury is running dry.");

If you need a binary choice (Yes / No), showHistoricEvent is not the right tool — you need the Campaign.raiseEvent method with isChoice = true. See the separate Player Choice Events tutorial.

Enable detailed logs by adding these to your REX launch options:

enable_logging verbose_script_logging

Logs land in the game’s log folder (the same place RR puts them).

Finding the Campaign object

The API documentation describes a singleton Campaign class, but the way it is exposed as a global can vary between REX builds. If ::campaign is not defined in yours, try ::game.campaign, or search the REX documentation and Discord for your version’s accessor. The object you want is the one with the raiseEvent, factionById, factionByName, and settlementByName methods.

Outro

Beyond what is covered here, REX Squirrel adds many quality‑of‑life improvements over the old scripting:

  • Real functions, so you can refactor repeated logic.
  • Classes and objects that mirror the game’s own data structures (Faction, Settlement, Army, Unit, Character, Region, …).
  • A live API reference in api.d.nut, plus auto‑generated docs from the REX team.
  • Hot script reloading via ::game.reloadScripts(), which carries the persistent table across and lets you iterate without restarting the game.

If you are new to Squirrel, start small: register a pluginLoad hook that logs a line, then add a campaignMapLoaded hook that gives the player money, then try a FactionTurnStart handler that reacts to the payload. Before long you will be writing scripts that simply were not possible in the old system.
